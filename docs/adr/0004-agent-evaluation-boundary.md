# Keep Agent Evaluation independent of the Wedding application

Status: accepted; revised for the September 2026 library-first evaluation workflow

Agent Evaluation is a separate bounded context in `tools/agent-evals`, with repository tasks, regression fixtures, profiles and rubrics under `evals`. Its primary authoring surface is a portable TypeScript library: tasks and runners produce recorded trials; versioned views prepare evidence; code and model graders define checks; a separate judge answers model questions. Pi, Jev and filesystem adapters own external effects. The Wedding application does not import evaluation code.

The primary workflow is one diagnostic trial against the pinned Wedding checkout, followed by inspection and repeated grading of its saved evidence. Native Pi execution retains the existing isolation, incremental recording and independent post-edit acceptance infrastructure. Authored and synthetic fixtures test the infrastructure; they are labeled separately from observed agent behavior. The production-linked Pi sandbox and application credentials remain excluded.

Native Pi resource discovery uses the original checkout's actual trust policy. The adapter records the selected and effective resources and preserves native provider/authentication and reasoning. Profiles may explicitly select an available agent model without changing global settings; saved defaults and effective selection are recorded separately. Its isolated four-tool surface still suppresses optional extension/package code; this explicit limitation prevents extrapolating to the user's complete interactive extension setup. Native conversation settings and an explicit controlled ablation are separate configurations.

Trials are immutable saved inputs. A view produces typed evidence with its scope, source references, omissions, applicability and coverage gaps; graders sharing that view prepare it once. Missing coverage yields an unknown verdict, while a required behavior absent from a complete recording can fail. Versioned evidence and grader identities survive regrading. Considered sources are distinct from explicit supporting sources.

The Jev judge batches independent categorical questions only when their submitted evidence envelopes match. Exact credential-free request bodies and version mappings are journaled before dispatch; responses retain the resolved model, probabilities, confidence and usage. The judge does not invent explanations or citations. Aggregate admission estimates, bounded requests, cancellation and no automatic retries keep live grading explicit. Estimates are application controls, not provider-enforced spending caps.

Regrading uses the same saved trial without rerunning Pi and appends a new grading record, including prepared evidence, questions, requests, responses and an inspection report. Changes to a question or view can therefore be evaluated without paying for another agent attempt. The existing registry-based CLI, saved-run format and paired experiments remain compatible; they are not prerequisites for authoring library graders.

The diagnostic example provides two model questions over a shared `diagnosis` view and a deterministic validation-order check over `validationHistory`. Successful transport, a favorable authored example or one repository trial does not establish semantic accuracy, human agreement, instruction effectiveness or generalization. Human calibration and broader experiment matrices remain separate work. See [package architecture](../../tools/agent-evals/README.md) and [Agent Evaluation](../../evals/README.md).
